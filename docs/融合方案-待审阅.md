## 三、换上 v2 求解器后，多出来的 6 个能力

| 能力 | 现在（成品）实测行为 | 融合后 |
|---|---|---|
| 「我想吃两个麦香鸡」 | **静默忽略** → 返回 `[OK]`，方案里根本没有麦香鸡 | 数量是**硬约束**，严格 2 件；菜单没有则明确报错而非静默 |
| 「不要饮料」 | **静默失效** → 燕麦奶铁仍在方案里 | 按 `category` 整类过滤（饮料→饮品） |
| 「不要冰的」 | 无此能力 | 菜单有 `temperature` 就过滤；没有就**如实披露**"未替你过滤任何商品" |
| 「来个辣堡」 | 连续子串匹配失败 → 无解 | 字符子序列匹配 → 麦辣鸡腿汉堡，并**明确告知对应关系** |
| 「想吃得划算」 | 无 | 映射 `objective=cheapest`，且不会把"划算"当成菜名 |
| 「预算吃满」策略 | 无 | 第四个 objective `max_value`，共 1~3 个方案供切换 |

另外顺带统一两个之前发现的历史口径问题：
- objective 命名：v2 内置 `OBJECTIVE_ALIASES`，`lowest_price → cheapest`，文档里的旧写法不再被 400 拒绝。
- 方案标签：统一为 **省钱优先 / 均衡推荐 / 最低卡 / 预算吃满**（此前 solver 与 normalize.js 文案不一致）。

## 四、必须处理的 6 个耦合点（不处理会坏）

1. **`ResultView.vue` 引了 `OrderPanel.vue`** —— 不做下单就必须删掉 import 与模板块，否则前端编译失败。
2. **mock 必须重跑** —— v2 solver 输出 `plans`（1~3 个），成品 mock 无此字段；不重跑则 mock 模式退化成单方案，前端 normalize 拿不到数据。
3. **`server/api.js` 必须加 `wants` 透传** —— 否则前端传了诉求，后端照样丢弃，等于白做。
4. **`EXCLUDE_OPTIONS` 必须合并** —— 品类忌口没有 UI 入口，求解器有能力也用不上。
5. **`ConstraintForm.vue` 当前是 modified 未提交状态**（定位功能在工作区里）—— 合并必须以工作区版本为底，不能拿 git HEAD 版，否则定位会丢。
6. **温度忌口在非 1450713 门店上必然"无法执行"** —— 这是 v2 设计的安全行为（不猜冷热），会落到 `notes` 里。所以 `note-banner` UI 必须一起上，否则用户看不到解释，反而以为失效。

## 五、融合后的效果

**演示链路**（一条不断）：
一句话点单 → 前端保底解析实时回填表单（含"想吃 X×2"chips）→ 提交 → 后端求解 → 1~3 个策略方案 → 手动改数量 / 从主菜单自主加菜 → 前端独立重算校验 → 未生效偏好显式披露。

**答辩现场能打的三张牌**：
1. **听得懂**：五槽位语义模型 + 数字归属判断（"两个人"不会变成"两个麦香鸡"）。
2. **算得准**：确定性枚举 + 分单位运算 + 前端独立重算校验，未知热量恒为 `null`。
3. **答得诚实**：做不到的事不假装做到——菜单没温度数据就说没数据，简称匹配就说匹配到了什么，券没用上就说为什么没用上。这是 v2 最值钱的部分，而成品目前是静默丢弃。

**一键启动不变**：`start.bat` 照旧起 3000 + 5173；`node scripts/demo-check.js` 从 6 项变 7 项（多"多方案 1~3 个"）。
